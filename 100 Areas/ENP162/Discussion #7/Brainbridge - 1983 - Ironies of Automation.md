## Introduction
Two ironies:
- Designer errors are a major source of operating problems
- Designers might try and eliminate the operator, but always wind up with an arbitrary set of tasks that they couldn't figure out how to automate which inevitably falls on the operator.
## 1. Tasks after automation
- Manual control skills. An operator could have skill atrophy, where if the system is down, after having not used it in so long they may not be able to properly work it. To remedy this, you would need to make the operator arguably more actively involved than without automation. Adding to the point that automation can make for more manual labor.
- Cognitive skills. Not likely to be remembered long term even if well performed short term in a class room (out of context) setting. Also, the intuition built by operators who used to run the machine is not transferrable to newer operators who haven't worked on the machine. 
- Monitoring. Its boring and impossible for someone to really pay attention. Also it is hard for the operator to truly see effectiveness of a computer task on a non-meta level as that is why the computer has been tasked with that.
- Operator attitudes. If the machine works, then the operator is bored and cannot maintain necessary skills. Moreover, a bad control system not designed for operator use sucks
## 2. Approaches to solutions
- Monitoring. Basically, it is most useful for the computer and system to somehow alert the operator. It is slightly paradoxical because the computer has to more or less know what the problem is, and then guide the operator to the problem. To that extent, alarms on alarms are simple solution.
- Working Storage. 

## 4. Conclusion
Take away from this paper, that there is great irony in automation in the way that it can add complexity to the system.
